## 1. 目的

- スライド発表のナレーションを、話しながらスライドを操作せずに録る。
- 「うまく録れたところまで OK を押し、失敗したら直前の OK 点へ戻って録り直す」操作で録音する。
- 録った音声とスライドの切り替えを合わせ、1 本の MP4 にする。
- 録音以外の作業（取り込み、点検、統合、動画化）は、LLM のエージェントがコマンドで実行できる。
- 録音の記録（撮り直しを含む）を、あとから LLM やプログラムが解析できる形で残す。
- GitHub で公開する。利用者は 1 人でも複数人でもよい。大学、企業、個人のどれでも使える。

## 2. 用語

| 用語 | 意味 |
|---|---|
| OK 点 | 本人が「ここまで採用する」と決めた位置。編集の操作である |
| 復旧できる位置 | 音声と、それを指す操作記録の両方が端末に書けた位置。保存の状態である |
| 録音ファイル | 録音したままの音声（raw）。捨てた区間も含む |
| 通しの位置 | 1 つの録音セッションの中で、録音ファイルをまたいで連続するサンプル位置 |
| 区間 | 録音の一部分。半開区間 [開始, 終了) で表す。状態は「採用」か「破棄」 |
| テイク | 1 枚のスライドを 1 回録ったもの。採用された区間の並び。同じスライドに複数あれば「候補」になる |
| 録音セッション | 1 台の端末で、1 つの発表を録ったもの |
| 統合セッション | PC で、複数の録音セッションを 1 つにまとめたもの |

「破棄」（撮り直しで捨てた区間）と「候補」（同じスライドの別のテイク。どちらも有効）は、別の状態として扱う。

## 3. 前提と全体の構成

### 3.1 前提

- 開発と動画化を行う PC：Windows 11、Core i7-13620H、メモリ 16GB、NVIDIA の GPU なし。PowerPoint（Microsoft 365）、Node.js、Python 3.12 がある。ffmpeg はない。
- 録音する端末：Android の Chrome、または PC の Chrome／Edge。Android の実機は USB デバッグで PC につなげる。
- ソフトのインストールとファイルのダウンロードは、名前、入手元、大きさを示し、利用者の許可を得てから行う。
- 利用者はプログラミングの経験を前提にしない。試験用の素材を利用者に用意させない。

### 3.2 構成

```
[PC] 台本パックを作る ─→ [スマホ／PC] ①録音アプリ（PWA）─→ 完成版 zip／全記録 zip
                                                              │
[PC] ②取り込み・統合 ←───────────────────────────────────────┘
        │
        ├─ ③点検・位置合わせ（faster-whisper、任意）
        └─ ④動画化（2 方式）─→ MP4 ─→ ⑤検証（予定表との差を実測）
```

| 部品 | 動く場所 | 作り |
|---|---|---|
| core（共通の処理） | ブラウザと Node.js | 依存なしの ES モジュール。操作記録の解釈、区間の計算、音声の作成、WAV、ZIP、SHA-256、音量、検証 |
| ①録音アプリ | Android／PC のブラウザ | PWA。core を使う |
| ②CLI `narrate` | PC（Node.js） | core を使う。`--json` で結果を返し、人に質問しない |
| ②取りまとめ画面 | PC のブラウザ | 同じ PWA の別の画面 |
| ③点検・位置合わせ | PC（Python） | faster-whisper |
| ④動画化、⑤検証 | PC | 方式 A：PowerShell＋PowerPoint の COM。方式 B と検証：Python（PyAV） |
| エージェント用の資料 | — | AGENTS.md、Claude Code 用のスキル、CLI を包むだけの MCP サーバー |

言語は素の JavaScript（ES モジュール、JSDoc の型注釈）とし、ビルドの手順を要らなくする。型の検査は TypeScript の checkJs で行う（開発時のみ）。

## 4. 録音アプリ（PWA）

### 4.1 画面

- 台本の取り込み：台本パック（6.1）を開く。複数の発表を端末に置ける。
- スライドの一覧：絵、番号、担当、状態（未収録／収録済み／要確認）、秒数。「自分の担当だけ」を表示できる。「担当 5 枚のうち 4 枚収録済み」「未収録へ移動」を出す。
- 録音の画面：スライドの絵、読む文（文字の大きさを変えられる）、このスライドの経過時間と目安、合計の時間と上限（設定した場合）、音量計、音割れの警告、残りの録音可能時間（推定）、復旧できる位置。
- 縦向きと横向き、明るい色と暗い色、日本語と英語に対応する。

### 4.2 操作

| 操作 | PC のキー | はたらき |
|---|---|---|
| 試し録り | T | 10 秒録って再生する。音量、音割れ、雑音を本人が確かめる |
| 録音開始／再開 | R | 押したらすぐ録音する（カウントダウンは無い。2026-11-20 に廃止） |
| OK（ここまで採用） | Space | 今の位置を OK 点にする |
| 撮り直し | Backspace | 最後の OK 点まで戻って一時停止する。続けて押すと、さらに前の OK 点へ戻る |
| 取り消し／やり直し | Ctrl+Z／Ctrl+Y | OK、撮り直し、区切りの操作を取り消す、やり直す |
| 次のスライドへ | Enter | OK を押したうえで、スライドの区切りを記録する |
| 直前を聞く | L | 最後の OK 点までの 5 秒を再生する |
| 通して聞く | P | 今のスライド、または全体を、つないだ状態で再生する |
| 印を付ける | M | 「ここは要確認」と記録する |
| 一時停止 | Esc | 録音を止める |

- キーの割り当ては変更できる。Bluetooth のキーボードやプレゼン用のリモコンでも操作できる（画面に触れないので、タップの音が入らない）。
- 任意のスライドを選んで、あとから録り直せる。以前のテイクは候補として残す。

### 4.3 つなぎ目

- 自動で音を切り落とさない。つなぎ目には短いフェード（初期値は前後 8 ミリ秒）だけをかける。
- つなぎ目の調整画面：波形を表示し、前の区間の終わりと、次の区間の始まりを 10 ミリ秒単位で動かせる。試聴できる。調整は編集の記録（6.4）に保存し、元の音声は変えない。取り消せる。
- 無音の長さをそろえる機能は提案を表示するだけにし、本人が選んだときにだけ適用する。

### 4.4 録音と保存

- 取得：getUserMedia＋AudioWorklet で非圧縮の PCM を取る。MediaRecorder は使わない。
- 設定：echoCancellation と autoGainControl は切ることを要求する。noiseSuppression は選べる。要求した値と、getSettings() が返した値を別々に記録する。返されない項目は「不明」と記録する。
- サンプリング周波数は、実際の値を録音ファイルごとに記録する。
- 録音バックエンド（差し替え可能な部品）の責任範囲：音声の取得、連番付け、端末への書き込み、復旧できる位置の返却、中断の理由の記録。Web 版では専用の Worker が OPFS の同期アクセスで追記し、約 1 秒ごとに flush する。
- 書き込みの順序：音声を書いて flush する → その位置を指す「保存位置の記録」（durable。6.3）を操作記録に書いて flush する → 画面の「復旧できる位置」（記録の番号とサンプル位置）を進める。
- 保存位置の記録は、本人の OK とは関係なく、録音中は約 1 秒ごとに書く。一度も OK を押していなくても、復旧できる位置が決まる。
- 複数のファイルを一括で確定する仕組みはない。そのため、「音声だけ書けて、記録が書けていない」状態が起こりうる前提で、復旧の手順（4.5）を作る。
- 起動時に navigator.storage.persist() を求め、結果を記録して表示する。
- 残りの録音可能時間は、navigator.storage.estimate() からの推定として表示する。足りなくなる前に警告し、止める。

### 4.5 中断と復旧

- Screen Wake Lock で画面が消えないようにする。解除されたら再取得を試み、状態を表示する。
- visibilitychange、マイクのトラックの mute／ended、AudioContext の状態の変化を検知したら、一時停止して理由を記録する。通知が来ないまま破棄される場合があるので、保存は 4.4 の書き込みに頼る。
- 次に開いたときの手順：
  1. 操作記録の末尾が途中で切れていれば、切れた行を捨てる。
  2. 録音ファイルの実際の長さと、操作記録が指す位置を照らし合わせる。
  3. 結果を「recovered」として記録し、次のように表示する。
     **「原音は 1:42 まで復旧。最後の OK は 1:35。続きの 7 秒を聞く」**
  4. 本人が、続きを採用する（OK にする）か、最後の OK 点から撮り直すかを選ぶ。マイクは自動で再開しない。

### 4.6 書き出し

利用者は、次の 3 種類から 1 つ以上を選ぶ。中身は重ならない。

| 種類 | 中身 | 大きさ（48kHz、16 ビット、モノラル） |
|---|---|---|
| 完成版 | スライド別の完成した音声（WAV）、manifest、台本、適用した処理の記録 | 完成した音声 1 分あたり約 5.8MB |
| 全記録 | 録音ファイル（破棄した区間を含む）、操作記録、区間の一覧、編集の記録、manifest、台本、README | 録音した総時間 1 分あたり約 5.8MB |
| 軽量音声（任意） | スライド別の Opus（Ogg）。試聴と送付用。正本は WAV | 1 分あたり約 0.25MB（32kbps） |

- 完成版は、全記録から PC で作り直せる。通しの音声は PC で作る。
- 「台本パックを同梱する」を選べる（スライドの絵を持たない相手に渡す場合）。
- 書き出しの前に、含まれるもの（音声、台本の文、操作の履歴、端末の情報）を一覧で見せる。全記録を選んだときは「撮り直した声も含みます」と表示する。
- ZIP は無圧縮で、OPFS に少しずつ書く。全体をメモリに載せない。失敗しても元の録音は残り、やり直せる。
- 大きい場合は巻に分ける（7 章）。1 巻を作り、端末への保存を確かめてから、次の巻を作る。必要な空きは 1 巻分で済む。
- 標準の手順は「ZIP を端末に保存」。画面に「保存後は『ファイル』から Google ドライブなどへ共有できます」と表示する。
- Web Share は追加の機能とする。実際のファイルで navigator.canShare({files}) が真のときにだけボタンを出す（ZIP は対象外。50MiB 以下の .wav や .opus が対象）。
- 軽量音声は WebCodecs の Opus で符号化し、Ogg に組み立てる（RFC 7845 のヘッダー、先頭の読み飛ばし、再生位置、末尾の処理に従う）。別の実装のデコーダーで、先頭の音、末尾の音、長さを照合する試験を行う。使えない端末ではボタンを出さず、PC 側で完成した WAV から作れるようにする。

### 4.7 端末内のデータの管理

- 発表ごとに、端末内の録音と台本の大きさを表示し、削除できる。
- 書き出して渡したあとに、削除を案内する。

### 4.8 オフラインと通信

- 初回の読み込みのあとは、機内モードでも、台本を開く、録音、復旧、ZIP の保存までできる。
- 外部の解析、CDN、フォントを使わない。Content-Security-Policy で接続先を自分のオリジンだけにする。
- 録音と書き出しの間、台本と音声は、自分のオリジンへも送らない。
- 説明の文言は「録音と台本は端末内で処理し、アプリからサーバーへ自動送信しません」とする。「一切通信しません」とは書かない。

### 4.9 ネイティブ版（最後の段階）

- 画面を消したままの録音などに向けて、Capacitor で包んだ Android 版を作る。マイク用のフォアグラウンドサービスを使う。
- ネイティブ版では、サービスが「取得から端末への書き込み、復旧できる位置の確定」までを受け持つ。画面を閉じても続き、再び開いた画面が状態を読み直す。
- Web 版と共通にするのは、操作、ファイルの形式、復旧の結果である。この境界（4.4 の録音バックエンドの責任範囲）は第 1 段階で決める。
- マイクの権限、開始のときの制約、通話や他のアプリとの競合は、中断の理由として記録する。

## 5. PC 側

### 5.1 CLI `narrate`

| コマンド | はたらき |
|---|---|
| `pack` | pptx から台本パックを作る（PowerPoint の COM でノートと絵を取り出す）。Markdown や JSON の台本と画像からも作れる |
| `import` | 完成版 zip／全記録 zip（複数の巻を含む）を取り込む。6.6 の決まりで統合し、検証する。欠けた巻を知らせる |
| `status` | スライドごとの状態（未収録／候補 1 件／候補 2 件以上／要確認／台本の版の食い違い）、合計の時間を返す |
| `select` | 候補が複数あるスライドで、採用するものを選ぶ。自動では上書きしない |
| `render` | 全記録から完成した音声を作る。通しの音声、軽量音声も作る |
| `check` | 文字起こしと台本の照合（8.1） |
| `align` | 外部で録った通しの音声を、スライドごとに分ける（8.2） |
| `build` | 動画を作る（8.3） |
| `verify` | 作った MP4 を測り、予定表との差を報告する（8.4） |
| `split-takes` | 破棄した区間も含め、区間ごとの WAV に切り出す |
| `validate` | 形式（JSON Schema）とハッシュだけを検証する |

`import`、`render`、`build` は、対応する台本パックを指定できる。台本のハッシュで一致を確かめる。

### 5.2 取りまとめ画面

- 複数の zip を読み込み、スライドごとの状態を表で見せる。
- 候補を聞き比べて採用を選ぶ。話す人ごとの音量の差を見せ、そろえるかどうかを選ぶ。
- 結果は、CLI と同じ形式の統合セッションとして保存する。

### 5.3 音量

- 測り方は ITU-R BS.1770 に従う。採用された区間だけを測る。
- 目標の値（初期値は −16 LUFS、ピークは −1.5 dBTP 以下。変更可）と、リミッターの動作は、レンダー仕様（6.4）で定める。
- 倍率は編集の記録に保存する。完成版には「適用した処理」を記録し、取り込んだあとに二重にかけない。

## 6. 形式（公開する仕様）

すべて UTF-8。JSON Schema（2020-12）を公開する。

### 6.1 台本パック

```
script-pack.zip
  script.json       … projectId、題名、台本のハッシュ、スライドの配列
  slides/0001.png … スライドの絵
```

- スライドごとの項目：slideId、順番、見出し、読む文、目安の秒数、担当、録音の対象かどうか、文のハッシュ、絵のハッシュ。
- slideId は「projectId＋pptx の SlideID」から作る。pptx 以外から作る場合は、`pack` が発行して台本に書き込む。
- 文のハッシュ：そのスライドの「slideId、読む文、録音の対象かどうか」を、キーの順と改行を決めた JSON にして SHA-256 を取る。
- 台本のハッシュ：全スライドの文のハッシュを順番に並べたものの SHA-256。題名、担当、目安の秒数、絵は含めない。
- これにより、文が変わったスライドだけを「版の食い違い」として知らせられる。絵だけが変わった場合は、音声をそのまま使える。
- ノートから省く部分と、目安の秒数の読み取り方は、設定ファイルの正規表現で指定する。

### 6.2 全記録

```
<projectId>_<sessionId>_full_v001.zip
  README.txt       … 構成と各項目の意味
  manifest.json    … 形式の版、アプリの版、projectId、台本のハッシュ、sessionId、exportId、
                     書き出しの種類、編集の版、巻の番号と総数、話す人の名前（任意）、端末の情報、
                     マイクの設定（要求と実際）、各ファイルの大きさと SHA-256（manifest 自身を除く）
  script.json
  events.jsonl     … 操作記録（6.3）
  segments.json    … 区間とテイクの一覧（操作記録から作ったもの）
  edits.json       … 編集の記録（6.4）
  raw/rec-000001.wav, …
```

- 巻に分ける場合、各巻は単独で開ける ZIP とする。記録のファイル（README から edits.json まで）は第 1 巻に入れ、録音ファイルを巻に振り分ける。
- 各巻の manifest に、exportId、巻の番号、総数、その巻に入れたファイルのハッシュを書く。各巻は、これだけで中身を検証できる。
- 全巻の ZIP そのもののハッシュの一覧は、巻の中には入れない（最後の巻が、自分自身のハッシュを含むことになるため）。書き出しのあとに、独立した索引ファイル（<exportId>_index.json）として作る。

### 6.3 操作記録

- events.jsonl：1 行に 1 操作。共通の項目は seq、eventId、type、wallClock（ISO 8601）、端末内の経過時間。
- 位置を持つ操作は、rawFile、そのファイル内の sample、通しの位置を持つ。

| type | 対象 | 前の状態 | 結果 |
|---|---|---|---|
| session-start | — | — | 録音セッションを作る |
| test-rec | — | 停止中 | 試し録りをした事実だけを残す。位置は持たない |
| rec-start | slideId、takeId | 停止中 | 録音中になる |
| file-rotate | 前後の rawFile、通しの位置 | 録音中 | 録音ファイルを切り替える。録音は続く。1 つのテイクが複数の録音ファイルを参照できる |
| durable | 位置 | 録音中 | 「ここまで端末に書けた」という保存位置を残す。約 1 秒ごと。区間の採用と破棄には影響しない |
| ok | 位置 | 録音中 | OK 点（checkpointId）を作る |
| retake | 戻る先の checkpointId | 録音中／停止中 | その OK 点より後の区間を破棄にし、一時停止する。続けて押した場合も、戻る先を明示するので一意に決まる |
| next-slide | 位置、次の slideId | 録音中 | OK 点を作り、テイクを閉じる |
| goto-slide | slideId | 停止中 | 対象のスライドを変える。既存のテイクは候補として残る |
| pause／resume | 理由 | — | 一時停止、再開 |
| recovered | 復旧できた位置、最後の checkpointId | 起動時 | 復旧の結果を残す |
| mark | 位置 | — | 要確認の印 |
| undo／redo | 対象の eventId | — | その操作を無効にする、有効に戻す。取り消したあとの新しい操作は、そのまま追記する |
| export | 種類、exportId | — | 書き出した事実を残す。位置は持たない |

- 操作記録が正本である。segments.json は操作記録から作れる。両方を入れるのは、解析する側が操作をたどらなくて済むようにするため。
- segments.json：区間（segmentId、takeId、slideId、参照する録音ファイルと [開始, 終了)、通しの位置、秒、状態、破棄の理由）と、テイク（takeId、slideId、区間の並び、状態）。
- 見本に「OK 点をまたいで録音ファイルが分かれ、撮り直しを取り消した例」を入れる。ブラウザ、CLI、外部のツールで、解釈が同じになることを照合できる。

### 6.4 編集の記録とレンダー仕様

- edits.json：つなぎ目の調整、フェードの長さ、音量の倍率、採用した候補、編集の版。
- 適用の順序：操作記録で「どの区間を採用するか」を決め、そのあとで編集の記録を適用する。編集の記録は、破棄した区間を採用に戻さない。
- 保証する範囲：**同じ入力の PCM、同じ編集の記録、同じレンダー仕様の版から、同じ完成 PCM を作る**（ブラウザと Node.js でビット単位に一致）。
- レンダー仕様で固定するもの：
  - 出力のサンプリング周波数（初期値 48kHz）と、変換の方法（係数を固定した窓付き sinc。係数は表として持つ）
  - フェードの形、フェードが重なる短い区間の扱い
  - 16 ビットへの丸めと飽和の方法
  - リミッターの動作と、処理のかたまりの間での状態の引き継ぎ
  - 実行する環境で結果が変わりうる数学関数を使わないこと
  - WAV のヘッダー（時刻などを入れない）
- 試験用の正解データ：空の入力、1 サンプル、44.1kHz から 48kHz への変換、かたまりの大きさを変えた場合。

### 6.5 完成版と統合セッション

- 完成版：manifest.json（適用した処理、レンダー仕様の版、編集の版を含む）、script.json、final/<slideId>.wav（大きい場合は順序付きで分割）。
- 統合セッション（PC）：取り込んだ各録音セッション、採用の選択、編集の記録、予定表（8.3）、作った音声と動画の一覧。

### 6.6 識別と取り込みの決まり

- 区別するもの：projectId、台本のハッシュ、sessionId、takeId、編集の版、書き出しの種類、exportId、巻の番号。
- 取り込みは、何度行っても、どの順番で行っても、同じ結果になる。

| 届いたもの | 扱い |
|---|---|
| すでに受け取った「exportId と巻の番号」の組 | 何もしない |
| ある書き出しの一部の巻だけ | 受け取った巻を記録して待つ。届く順番は問わない。全巻を検証できた時点で、取り込みを完了とする |
| 完成版だけがあるテイクの、全記録 | 録音ファイルと履歴を補う |
| 全記録があるテイクの、完成版（同じ編集の版） | 検証にだけ使う |
| 同じテイクの、編集の版が違う完成版 | 採用の候補として残す。自動では置き換えない |
| 同じスライドの、別の録音セッションのテイク | 候補として残す |
| 文のハッシュが合わないテイク | 「版の食い違い」として知らせる |
| 巻が欠けている、ハッシュが合わない | 取り込まずに知らせる |

## 7. 録音の長さについて

利用者への約束は、「**アプリ独自の録音時間の制限は設けない。残りの時間は推定で表示する**」とする。端末やブラウザの割り当てによる上限はある。

| 項目 | 対処 |
|---|---|
| メモリ | 録音、音声の作成、ZIP、ハッシュ、音量の測定は、すべて少しずつ読み書きする |
| ハッシュ | Web Crypto の digest() は入力の全体を必要とするので使わない。逐次に計算する SHA-256 を core に持つ |
| 録音ファイル | 録音開始ごと、および一定の大きさ（初期値 256MB、約 44 分）ごとに分ける |
| 完成した音声 | 通常の WAV は約 12 時間 26 分で 4GiB に達する。スライド別の WAV も、通しの WAV も、一定の大きさで順序付きに分割できる。動画化は順に読む |
| ZIP | ZIP64 に対応する（4GiB と 65,535 件の境界を、別の実装の読み手で検証する）。あわせて、一定の大きさ（初期値 1GB）ごとに、単独で開ける巻に分ける |
| 端末の容量 | 書き出しは 1 巻ずつ作る。録音と書き出しの前に、推定の空きと比べて警告する |
| 操作記録 | 追記のみ。起動を速くするため、解釈した状態を定期的に保存する（正本は操作記録） |
| スライドの枚数 | 一覧は、見えている部分だけを描く |
| 動画化 | 方式 A は、リンクでの参照を試し、だめなら作業用のコピーに埋め込む。長い動画は方式 B を使える |
| 文字起こし | `check` はスライドごとに処理する。`align` は、重なりを持たせた時間の窓で順に処理する（8.2） |

## 8. 点検、位置合わせ、動画化、検証

### 8.1 点検（`check`）

- faster-whisper（CPU、int8）。モデルは small を初期値とし、選べる。
- スライドごとの音声を文字に起こし、台本と並べた報告（JSON）を作る。
- 機械的に出す項目：文字の誤り率、長さの比、話す速さ、最も近い台本はどのスライドか、音割れ、長い無音、音量。
- 「文が抜けている」「別のスライドの文を読んでいる」の最終的な判断は、報告を読んだ人または LLM が行う。
- initial_prompt に台本の語を入れる機能は、初期値では切る。

### 8.2 位置合わせ（`align`）

- 録音アプリを使わずに録った通しの音声を取り込む。
- 音声の全体を一度にメモリへ読まない。重なりを持たせた時間の窓で順に文字に起こし、元の音声のサンプル位置に戻す。
- 日本語は、句読点、全角と半角、数字の書き方をそろえてから、スライドの順に照らし合わせる。読み飛ばし、繰り返し、余談があってもよい方法を使う。
- 切れ目の候補には、根拠の語、時刻、次点の候補、確かさを付ける。確かさの低い切れ目は自動で確定せず、試聴して確定する。
- 結果は、録音アプリと同じ形式の操作記録として保存する（由来は align と記録する）。

### 8.3 動画化（`build`）

- 両方式に共通の**予定表**（timeline.json）を先に作る。スライドごとに、表示の開始、音声の配置の開始、音声の終了、前後の間を書く。前後の間の初期値は、前 0.3 秒、後 0.5 秒。

| | 方式 A：PowerPoint | 方式 B：直接合成 |
|---|---|---|
| 作り方 | コピーした pptx に音声を入れ、切り替えの時間を設定し、CreateVideo で書き出す | スライドの絵（PNG）と音声を、PyAV で MP4 にする |
| アニメーション、画面切り替え | 再現される | 再現されない |
| 時刻 | PowerPoint の動作による（実測する） | 音声はサンプル単位。絵は 1 フレーム（30fps で約 33 ミリ秒）の刻み |
| 必要なもの | PowerPoint | Python と PyAV、スライドの絵 |

- 方式 A：
  - 同じ 3 枚のスライドで、リンク版と埋め込み版の両方を書き出し、MP4 を復号して各スライドの音を照合する。リンク版がだめなら、作業用のコピーへの埋め込みを使う。
  - クリックを待つアニメーションは、既存のタイミングがあればそれを使う。なければ「未設定」として知らせ、推測で進めない。
  - WithWindow を偽にして開く。利用者が開いている他のプレゼンテーションに触れない。PowerPoint がすでに動いていれば、終了させない。
- 方式 B：
  - 比較の出発点は、1080p、30fps 固定、H.264、yuv420p、AAC 48kHz。対象の PC で実際に符号化と復号を行って確かめる。
  - 各スライドの境界は、最初からの累積のサンプル位置をフレームに丸めて決める。丸めの誤差を積み上げない。
- どちらを初期値にするかは、静止画中心の発表と、アニメーションのある発表で、画質、同期、所要時間を測って決める。
- 共通：元の pptx は変更しない。毎回、元の pptx と統合セッションから作り直す。
- PyAV の Windows 用の配布物には FFmpeg のライブラリが入っており、x264 と x265 を含む。本ツールは PyAV を同梱せず、利用者がインストールする。依存する部品の利用条件は、本体の MIT とは別に文書に書く。

### 8.4 検証（`verify`）

- MP4 を PyAV で読み、絵が切り替わった時刻と、音声が始まった時刻を測る。**予定表の各時刻との差**を報告する。
- 合格の条件：方式 B は、音声 20 ミリ秒以内、絵 1 フレーム以内。方式 A は、50 ミリ秒以内を目標とし、実測の結果で確定する。
- 同じ絵が続くなど、映像から境界が分からない場合は「測定不能」を返す。
- 合計の長さ、音声の欠落、無音の区間も報告する。

## 9. LLM からの操作と、渡る情報

- CLI はすべて `--json` で結果を返し、終了コードで成否を示す。長い処理は、進み具合を 1 行ずつの JSON で出す。
- AGENTS.md とスキルに、手順と判断の基準を書く。MCP サーバーは CLI を包むだけにする。
- 録音アプリは端末の中だけで動く。一方、PC で LLM のエージェントに点検や統合をさせると、台本、文字起こし、報告が、その LLM のサービスに渡る。この 2 つを、説明の中で分けて書く。
- LLM を使わなくても、機械的に出す項目だけで点検できるようにする。

## 11. 試験の計画

### 11.1 素材

- **スライド**（pptxgenjs で作る）：3 枚の最小のもの（スライドごとに固有の色と番号）、15 枚程度の日本語の発表、200 枚の長いもの、意地の悪いもの（非表示、空のノート、長いノート、絵文字、既存のアニメーションや音声、日本語や空白を含むファイル名）、英語のもの。
- **原稿**：自作する。
- **音声**：Windows の音声合成（日本語と英語、複数の声）で文ごとに作る。操作記録の解釈と音声の作成の正解として使う。声の立ち上がりの位置の正解としては使わない。
- **確認音**：連番を読み取れる合図の音。スライドごとに固有の音。
- **音質を悪くしたもの**：雑音（白色、ピンク、人の話し声、50Hz のうなり。信号対雑音比 30／20／10／0dB）、音割れ、小さい音量、残響、8kHz、16kHz、44.1kHz、途切れ、タップの音、息や破裂音、長い無音、背景の音楽、直流のずれ。
- **撮り直しを含むセッション**：正解が分かる形で、操作の列を自動で作る。
- **実際の人の声と発表**（入手の前に、対象、大きさ、利用条件を示して許可を得る）：

| 素材 | 使い道 | 確かめたこと |
|---|---|---|
| Google FLEURS の日本語 | 人の読み上げの文字起こしの誤り | 配布の表示は CC BY 4.0（レビューで確認） |
| FOSDEM 2025 の講演「LibreOffice Accessibility on Linux, Windows and macOS」 | 自然な間、余談、実際の切り替えがある発表での位置合わせ | 講演のページを確認した。10 分、スライド（PDF）、字幕（VTT）、動画（WebM 42.5MB、MP4 257.2MB）。サイトの表示は CC BY 2.0 Belgium。言語はページに書かれていない |
| Mozilla Common Voice の日本語 | 音質がまちまちな声 | 未確認 |
| LibriVox の日本語の朗読 | 家庭で録られた声 | 「パブリックドメイン」は米国での扱い。日本での扱いは未確認なので、優先しない |

- 実際の発表では、開発側が目で見て付けた境界の時刻を正解として保存する。字幕は補助に使う。

### 11.2 試験の段階

| 段階 | 内容 | 合格の条件 |
|---|---|---|
| T1 core | 操作の列を無作為に作り、単純な別実装と比べる。WAV、ZIP、ZIP64、SHA-256 の往復。レンダー仕様の正解データ | すべて一致する |
| T2 流れ全体 | 正解の分かるセッションから音声を作る。複数端末の統合、候補の重なり、未収録、版の食い違い、壊れた zip、欠けた巻。**完成版だけで動画化、全記録だけから作り直し、両方を逆の順に取り込み、巻の順不同と再送（第 2 巻が先着 → 第 1 巻 → 第 2 巻を再送）** | 完成した音声が正解とビット単位で一致する。取り込みの順番で結果が変わらない |
| T3 PWA（PC） | (1) 既知の PCM を直接流し、1 サンプル単位で保存を検証する。(2) Chrome の偽のマイク入力（WAV は必要に応じて変換され、指定しなければ繰り返し再生される）で、実時間の動作を検証する。(3) 強制終了を 3 か所で起こす（音声を書いた直後、記録を書いている途中、録音ファイルの切り替えの直前）。一度も OK を押さずに強制終了する場合も試す。(4) 通信の点検。(5) 24 時間分の量を作り、最後の巻の取り込みと通しの音声の再生まで行う | 欠落がない。表示した「復旧できる位置」まで再生できる。録音と書き出しの間、自分のオリジンにも台本と音声を送らない |
| T4 Android の実機 | 連番入りの確認音を PC から流して録る。アプリ内部の「取得したサンプル数」と「書き込んだサンプル数」も記録する。画面ロック、アプリの切り替え、強制終了を adb で起こす。着信は手作業。**USB を外し、ホーム画面から起動し、省電力の状態でも 1 回行う** | 前面で 60 分録って欠落がない。時計のゆるやかなずれと、瞬間的な欠落を分けて報告する。1GB の巻を PC で展開してハッシュが一致する |
| T5 動画化 | 方式 A（リンク版、埋め込み版）と方式 B で、最小のスライドから 2 時間の動画まで作る。**わざと 100 ミリ秒ずらした動画を、`verify` が見つけられることも試す** | 8.4 の条件を満たす |
| T6 点検と位置合わせ | 音質ごとの文字の誤り率。音声の入れ替えと文の抜けを見つけられるか。切れ目の誤差の中央値と 95 パーセンタイル。**誤った切れ目を自動で確定した割合と、確認に回した割合**。この PC での処理時間 | 数値を報告する。自動で確定してよい確かさの基準を決める |
| T7 実際の素材 | FLEURS と FOSDEM の講演で、T5 と T6 を行う | 合成音声との違いを報告する |

- 長い録音の試験は、まず分割の境界を小さくして壊れ方を調べ、そのあとで実時間の試験を行う。

## 12. 作る順番

1. **細い一本を通す**（技術の確かめを含む）

   - ここで決めるもの：録音バックエンドの責任範囲、操作記録の意味、識別と取り込みの決まり、予定表、方式 A のリンクと埋め込み
